# Default settings (archiving OFF) wal_level = replica archive_mode = off ← Archiving disabled archive_command = '' ← No command set

• Old WALs are recycled after checkpoint

📝 Step 1: Transaction Happens

Someone runs a SQL command:

psql -U postgres > INSERT INTO users VALUES (1, 'Alice'); > COMMIT;
⬇️

PostgreSQL writes to current WAL file:

📄 /var/lib/pgsql/15/data/pg_wal/00000001000000020000005E
Size: 14.2 MB / 16 MB
Status: Still being written to...
# What's happening internally: PostgreSQL → Writes transaction log → Current WAL: 005E → Size growing: 14.2 MB → 14.3 MB → 14.4 MB...
2
💯 Step 2: WAL Becomes Full (16MB)
✅ WAL file reaches 16MB!
PostgreSQL: "This segment is complete, switch to next one"
📦 /var/lib/pgsql/15/data/pg_wal/00000001000000020000005E
Size: 16.0 MB (FULL)
Status: ✅ Complete and closed
⬇️

PostgreSQL switches to next WAL:

📄 /var/lib/pgsql/15/data/pg_wal/00000001000000020000005F
Size: 0.1 MB / 16 MB
Status: Now active (being written)
# Directory now looks like: pg_wal/ ├── 00000001000000020000005E ← 16MB (FULL, ready) ├── 00000001000000020000005F ← 0.1MB (ACTIVE) └── 000000010000000200000060 ← 0MB (pre-allocated)
3
⚙️ Step 3: Enable WAL Archiving

Admin decides to enable archiving for PITR:

📝 Edit postgresql.conf
sudo vi /var/lib/pgsql/15/data/postgresql.conf # Add these lines: wal_level = replica archive_mode = on ← Turn ON archive_command = 'test ! -f /backups/wal_archive/%f && cp %p /backups/wal_archive/%f' archive_timeout = 60 ← Force archive every 60s
⬇️
# Create archive directory sudo mkdir -p /backups/wal_archive sudo chown postgres:postgres /backups/wal_archive sudo chmod 700 /backups/wal_archive # Restart PostgreSQL sudo systemctl restart postgresql-15
✅ Archiver process now running!
PostgreSQL starts monitoring pg_wal/ for completed segments
4
🚦 Step 4: Archive Status Flag Created

PostgreSQL sees completed WAL and creates flag:

🚩 /var/lib/pgsql/15/data/pg_wal/archive_status/00000001000000020000005E.ready
Size: 0 bytes (just a marker!)
Meaning: "Hey archiver! Copy file 005E!"
# What PostgreSQL does internally: touch pg_wal/archive_status/005E.ready # This tells the archiver process: "There's a WAL file ready to be archived"
⬇️

Current structure:

pg_wal/ ├── 005E ← 16MB (WAITING for archiver) └── 005F ← Active pg_wal/archive_status/ └── 005E.ready ← 0 bytes (FLAG FILE)
5
🚂 Step 5: Archiver Copies WAL File

Archiver process sees .ready flag and springs into action:

# Archiver builds the command: %p = /var/lib/pgsql/15/data/pg_wal/005E %f = 005E # Executes this command: test ! -f /backups/wal_archive/005E && \ cp /var/lib/pgsql/15/data/pg_wal/005E \ /backups/wal_archive/005E
🚂💨
✅ Copying... 16MB file
🚂 FROM: pg_wal/005E
🚂 TO: /backups/wal_archive/005E
📦 /backups/wal_archive/00000001000000020000005E
Size: 16.0 MB
Status: ✅ Successfully archived!
# Now files exist in TWO places: 1. pg_wal/005E ← Original (16MB) 2. /backups/wal_archive/005E ← Archived copy (16MB)
6
✅ Step 6: Mark as Archived (.done)

Archive command returns success (exit code 0):

# PostgreSQL does: mv pg_wal/archive_status/005E.ready \ pg_wal/archive_status/005E.done
⬇️
✅ /var/lib/pgsql/15/data/pg_wal/archive_status/00000001000000020000005E.done
Size: 0 bytes
Meaning: "Archiving complete!"
PostgreSQL log shows:
2025-11-08 10:01:23 UTC [12345] LOG: archived write-ahead log file "00000001000000020000005E"
# Current state: pg_wal/ ├── 005E ← Still here (will be recycled after checkpoint) └── 005F ← Active pg_wal/archive_status/ └── 005E.done ← Changed from .ready to .done /backups/wal_archive/ └── 005E ← Safe archived copy!
7
💾 Step 7: Taking Base Backup (pg_basebackup)

Now you run a base backup:

pg_basebackup -D /backups/base_2025-11-08 \ -Ft -z -X stream -P
⬇️

What happens with -X stream:

✅ PostgreSQL STREAMS WAL directly through network
• Doesn't read from pg_wal/ directory
• Doesn't care if files are deleted
• Captures WAL in real-time during backup
# pg_basebackup creates: /backups/base_2025-11-08/ ├── base.tar.gz ← Data files snapshot ├── pg_wal.tar.gz ← WAL needed for consistency │ (streamed, not from disk!) └── backup_manifest ← Verification info
🤔 Important Point:
• pg_wal/ might have: 005D, 005E, 005F (on disk)
• But backup WAL: might be 005E or 005F (streamed)
• They're INDEPENDENT!
8
🎯 Step 8: Your Question - What If File Missing?

Scenario: What if 005E gets deleted before backup?

❌ If using -X fetch:
Timeline: 10:00 - WAL 005E archived and deleted from pg_wal/ 10:05 - pg_basebackup -X fetch runs 10:06 - ERROR! Can't find 005E in pg_wal/ Backup FAILS! ❌
BUT...
✅ Using -X stream (SAFE):
Timeline: 10:00 - WAL 005E archived and deleted from pg_wal/ 10:05 - pg_basebackup -X stream runs 10:06 - PostgreSQL STREAMS current WAL in real-time Doesn't need 005E from disk Backup SUCCESS! ✅
✅ Using -X none + WAL archive (PRO):
Timeline: 10:00 - WAL 005E archived to /backups/wal_archive/ 10:05 - pg_basebackup -X none (no WAL in backup) 10:06 - Backup contains no WAL files During RESTORE: → PostgreSQL reads from /backups/wal_archive/ → Pulls ALL needed WALs from archive → PITR works perfectly! ✅
# Final state shows THREE copies: 1. pg_wal/005E ├─ May be deleted/recycled after checkpoint └─ Temporary working directory 2. /backups/wal_archive/005E ├─ PERMANENT archived copy └─ Used for PITR 3. /backups/base_XXX/pg_wal.tar.gz ├─ Contains WAL for THIS backup └─ Self-contained snapshot
