🎯 How It All Works Together

  • Mac is your Ansible controller where you write and run playbooks
  • Ubuntu Host runs Vagrant which creates and manages the PostgreSQL VM
  • PostgreSQL VM is the target where PostgreSQL will be installed
  • Mac connects directly to the VM via SSH using the Vagrant-generated private key
  • Ansible is "agentless" - no software needs to be installed on the VM
  • All configuration changes are pushed from Mac to VM over SSH

📋 Complete Step-by-Step Guide with Commands

Follow each step carefully. Every command is explained in detail.

1
🐧 Ubuntu Host
Find the Vagrant SSH Key
Purpose: Locate the private SSH key that Vagrant automatically generated when it created the PostgreSQL VM. This key is needed to authenticate SSH connections.
Navigate to Vagrant project directory
cd /proj/vagrant/vagrant-lab # Changes to the directory where Vagrantfile exists
View SSH configuration for the VM
vagrant ssh-config postgresdb # Shows SSH connection details for 'postgresdb' VM # Including hostname, port, user, and IdentityFile (private key path)
Host postgresdb HostName 192.168.1.169 User vagrant IdentityFile /proj/vagrant/vagrant-lab/.vagrant/machines/postgresdb/virtualbox/private_key Port 22
Extract just the key path
vagrant ssh-config postgresdb | grep IdentityFile # Filters output to show only the IdentityFile line # This is the path we need to copy from

💡 What's Happening?

  • Vagrant creates a unique SSH key pair for each VM
  • The private key is stored in .vagrant/machines/[vm-name]/virtualbox/
  • This key allows passwordless SSH access to the VM
  • We need to copy this key to the Mac so Ansible can use it
2
🖥️ Mac
Copy SSH Key from Ubuntu to Mac
Purpose: Transfer the Vagrant private key from the Ubuntu host to your Mac's SSH directory. This enables your Mac to authenticate with the PostgreSQL VM.
Copy the private key using SCP (Secure Copy)
scp krishna@192.168.1.120:/proj/vagrant/vagrant-lab/.vagrant/machines/postgresdb/virtualbox/private_key ~/.ssh/postgresdb_key # Breakdown: # scp - Secure copy command # krishna@192.168.1.120 - Username and IP of Ubuntu host # :/proj/vagrant/... - Source path on Ubuntu (the Vagrant key) # ~/.ssh/postgresdb_key - Destination path on Mac
krishna@192.168.1.120's password: [enter password] private_key 100% 1675 1.6MB/s 00:00
Set correct file permissions (CRITICAL)
chmod 600 ~/.ssh/postgresdb_key # chmod 600 means: # 6 (owner): read + write # 0 (group): no permissions # 0 (others): no permissions # SSH requires private keys to have strict permissions for security
Verify the key was copied successfully
ls -la ~/.ssh/postgresdb_key # -l shows detailed info # -a shows hidden files # Should display: -rw------- (600 permissions)
-rw------- 1 gopal staff 1675 Oct 29 10:30 /Users/gopal/.ssh/postgresdb_key

💡 What's Happening?

  • scp securely transfers files over SSH between machines
  • The key is copied to ~/.ssh/ (standard location for SSH keys)
  • chmod 600 is mandatory - SSH will reject keys with wrong permissions
  • This key is now ready to be used by Ansible for authentication
3
🖥️ Mac
Test SSH Connection to PostgreSQL VM
Purpose: Verify that you can successfully connect to the PostgreSQL VM from your Mac using the copied SSH key. This confirms network connectivity and key authentication.
Connect to VM using SSH with the private key
ssh -i ~/.ssh/postgresdb_key vagrant@192.168.1.169 # Breakdown: # ssh - SSH client command # -i ~/.ssh/postgresdb_key - Identity file (private key) to use # vagrant@192.168.1.169 - username@hostname # vagrant = default Vagrant username # 192.168.1.169 = VM's IP address
Welcome to Ubuntu 20.04.6 LTS (GNU/Linux 5.4.0-150-generic x86_64) vagrant@postgresdb:~$ ← You're now inside the VM!
Check you're on the correct machine
# Run these commands inside the VM to verify: hostname # Should output: postgresdb ip addr show # Should show IP: 192.168.1.169 whoami # Should output: vagrant
Exit back to your Mac
exit # Or press Ctrl+D to disconnect # Returns you to Mac terminal
logout Connection to 192.168.1.169 closed. gopal@MacBook ~ % ← Back on Mac

💡 What's Happening?

  • SSH establishes an encrypted connection to the VM
  • The -i flag tells SSH which private key to use for authentication
  • If successful, you get a shell prompt on the remote VM
  • This confirms: network is working, key is correct, and VM is accessible
  • Ansible will use the same mechanism to connect and run commands

🖥️ Mac
Navigate to Ansible Project Directory
Purpose: Move to your Ansible project folder where you'll create configuration files, inventory, and playbooks.
Change to Ansible project directory
cd ~/Desktop/Devops/concepts/ansible-lab # ~/ represents your home directory # This path should exist; if not, create it first
Create directory structure (if not exists)

. ├── inventory/ ├── playbooks/ └── roles/

💡 What's Happening?

  • inventory/ contains files defining which servers to manage
  • playbooks/ contains automation scripts (YAML files)

5
🖥️ Mac
Create Ansible Inventory File
Purpose: Define the PostgreSQL VM as a managed host in Ansible's inventory. This tells Ansible what servers exist and how to connect to them.
Create inventory file
nano inventory/inventory.ini # Or use: vim, code, or any text editor
Add the following content
[db_servers] postgresdb ansible_host=192.168.1.169 ansible_user=vagrant ansible_ssh_private_key_file=~/.ssh/postgresdb_key [db_servers:vars] ansible_python_interpreter=/usr/bin/python3 # Explanation: # [db_servers] - Group name for database servers # postgresdb - Inventory hostname (alias) # ansible_host=192.168.1.169 - Actual IP address to connect to # ansible_user=vagrant - SSH username # ansible_ssh_private_key_file= - Path to private key # [db_servers:vars] - Variables for this group # ansible_python_interpreter= - Python path on remote host
Save and verify the file
# In nano: Ctrl+O (save), Enter, Ctrl+X (exit) cat inventory/inventory.ini # Display file contents to verify

💡 Understanding Inventory Parameters

  • [db_servers] - Creates a group; you can target all DB servers at once
  • ansible_host - The actual IP/hostname to connect to
  • ansible_user - Remote username for SSH connection
  • ansible_ssh_private_key_file - Which SSH key to use
  • ansible_python_interpreter - Required for Python 3 systems
  • Groups allow you to manage multiple servers with one command
6
🖥️ Mac
Configure Ansible Settings
Purpose: Create ansible.cfg to configure Ansible's behavior. This file defines defaults like inventory location, timeout values, and privilege escalation.
Create ansible.cfg in project root
nano ansible.cfg
Add comprehensive configuration
[defaults] inventory = ./inventory/inventory.ini roles_path = ./roles host_key_checking = False retry_files_enabled = False timeout = 30 interpreter_python = auto_silent [privilege_escalation] become = True become_method = sudo become_user = root become_ask_pass = False # [defaults] section: # inventory - Path to inventory file # roles_path - Where to find roles # host_key_checking - Skip SSH host key verification (dev only!) # retry_files_enabled - Don't create .retry files on failure # timeout - SSH connection timeout in seconds # interpreter_python - Auto-detect Python on remote host # [privilege_escalation] section: # become - Enable privilege escalation # become_method - Use sudo for privilege escalation # become_user - Escalate to root user # become_ask_pass - Don't prompt for sudo password (vagrant has NOPASSWD)
Verify configuration syntax
ansible --version # Should show: # - Ansible version # - Config file location # - Python version
ansible [core 2.15.4] config file = /Users/gopal/Desktop/Devops/concepts/ansible-lab/ansible.cfg configured module search path = ['/Users/gopal/.ansible/plugins/modules'] ansible python module location = /usr/local/lib/python3.11/site-packages/ansible python version = 3.11.5

💡 Configuration Explained

  • host_key_checking = False - Useful for testing, but disable in production
  • become = True - Automatically use sudo for tasks requiring root
  • timeout = 30 - Prevents hanging on slow networks
  • Ansible looks for config in: current dir > ~/.ansible.cfg > /etc/ansible/ansible.cfg
  • Project-specific config (current dir) takes highest priority

🖥️ Mac
Test Ansible Connectivity
Purpose: Use Ansible's ping module to verify that Ansible can successfully connect to the PostgreSQL VM. This tests SSH, authentication, and Python availability.
Basic connectivity test
ansible all -m ping # Breakdown: # ansible - Ansible ad-hoc command tool # all - Target all hosts in inventory # -m ping - Use the 'ping' module (not ICMP, but connection test)
postgresdb | SUCCESS => { "ansible_facts": { "discovered_interpreter_python": "/usr/bin/python3" }, "changed": false, "ping": "pong" }
Verbose output for debugging
ansible all -m ping -vvv # -v = verbose # -vv = more verbose # -vvv = very verbose (shows SSH commands, file transfers, etc.) # Use verbose mode when troubleshooting connection issues
Target specific host or group
ansible postgresdb -m ping # Ping only the 'postgresdb' host ansible db_servers -m ping # Ping all hosts in 'db_servers' group
Test with a different module
ansible all -m command -a "uptime" # Run 'uptime' command on all hosts ansible all -m setup # Gather all facts about the hosts (detailed system info)

💡 What Does Ping Actually Do?

  • Ansible's ping is NOT an ICMP ping - it's a Python connectivity test
  • Connects via SSH, runs Python code, returns "pong" if successful
  • Tests: SSH connection, authentication, Python availability, sudo access
  • "changed": false means no changes were made to the system
  • If this works, you're ready to run real playbooks!

Install PostgreSQL Ansible Collection
Purpose: Install the community.postgresql collection which provides modules for managing PostgreSQL databases, users, and permissions.
Install PostgreSQL collection from Ansible Galaxy
ansible-galaxy collection install community.postgresql # Breakdown: # ansible-galaxy - Tool for managing Ansible content # collection install - Install a collection (bundle of modules/roles) # community.postgresql - Collection name from Ansible Galaxy
Starting galaxy collection install process Process install dependency map Starting collection install process Downloading https://galaxy.ansible.com/download/community-postgresql-3.4.0.tar.gz Installing 'community.postgresql:3.4.0' to '/Users/gopal/.ansible/collections/ansible_collections/community/postgresql' community.postgresql:3.4.0 was installed successfully
Verify installation
ansible-galaxy collection list | grep postgresql # Should show the installed collection and version
community.postgresql 3.4.0
View collection documentation
ansible-doc community.postgresql.postgresql_db # Shows documentation for the postgresql_db module ansible-doc community.postgresql.postgresql_user # Shows documentation for the postgresql_user module

💡 Understanding Ansible Collections

  • Collections are the modern way to package Ansible content
  • They bundle modules, plugins, roles, and documentation together
  • community.postgresql provides: postgresql_db, postgresql_user, postgresql_privs, etc.
  • Collections are installed to ~/.ansible/collections/
  • Use namespaced names in playbooks: community.postgresql.postgresql_db

🖥️ Mac
Create and Run PostgreSQL Playbook
Purpose: Create a playbook that installs PostgreSQL, configures it, and creates a database. Then execute it to automate the entire setup.
Create the playbook file
nano playbooks/install_postgres.yml
Add playbook content (see Playbooks tab for full example)
--- - name: Install and Configure PostgreSQL hosts: db_servers become: yes tasks: - name: Update apt cache apt: update_cache: yes cache_valid_time: 3600 - name: Install PostgreSQL apt: name: - postgresql - postgresql-contrib - python3-psycopg2 state: present - name: Ensure PostgreSQL is running service: name: postgresql state: started enabled: yes # See full playbook in the Playbooks section
Check playbook syntax before running
ansible-playbook playbooks/install_postgres.yml --syntax-check # --syntax-check validates YAML syntax without executing # Catches errors before running the playbook
playbook: playbooks/install_postgres.yml
Dry run (check mode)
ansible-playbook playbooks/install_postgres.yml --check # --check runs in "dry run" mode # Shows what WOULD change without actually making changes # Not all modules support check mode
Run the playbook for real
ansible-playbook playbooks/install_postgres.yml # Executes all tasks in the playbook # Shows progress and results for each task
PLAY [Install and Configure PostgreSQL] ******************************** TASK [Gathering Facts] ************************************************* ok: [postgresdb] TASK [Update apt cache] ************************************************ changed: [postgresdb] TASK [Install PostgreSQL] ********************************************** changed: [postgresdb] TASK [Ensure PostgreSQL is running] ************************************ ok: [postgresdb] PLAY RECAP ************************************************************* postgresdb : ok=4 changed=2 unreachable=0 failed=0
Run with verbose output
ansible-playbook playbooks/install_postgres.yml -vvv # Shows detailed execution information # Useful for debugging issues

💡 Understanding Playbook Output

  • ok - Task ran successfully, no changes needed
  • changed - Task ran and made changes to the system
  • failed - Task encountered an error
  • skipped - Task was skipped due to conditions
  • unreachable - Couldn't connect to the host
  • Ansible is idempotent - running again won't change anything if already configured

🐘 PostgreSQL VM
Fix Sudo Warning (Optional but Recommended)
Purpose: Remove the "sudo: unable to resolve host" and secure_path warning that appears when running Ansible commands. This is a cosmetic fix that cleans up the output.
First, understand the warning
# When Ansible runs sudo commands, you might see: sudo: unable to resolve host postgresdb: Name or service not known sudo: setrlimit(RLIMIT_CORE): Operation not permitted # This happens because: # 1. Hostname isn't in /etc/hosts # 2. sudo secure_path may be restrictive for Vagrant user
SSH into the VM (if not already connected)
ssh -i ~/.ssh/postgresdb_key vagrant@192.168.1.169
Fix 1: Add hostname to /etc/hosts
sudo nano /etc/hosts # Add this line at the end: 127.0.0.1 postgresdb # Save and exit: Ctrl+O, Enter, Ctrl+X
Verify the hostname resolution
hostname # Should output: postgresdb ping -c 1 postgresdb # Should successfully ping 127.0.0.1
PING postgresdb (127.0.0.1) 56(84) bytes of data. 64 bytes from postgresdb (127.0.0.1): icmp_seq=1 ttl=64 time=0.024 ms
Fix 2: Configure sudo for vagrant user
sudo visudo # This opens the sudoers file safely # Find the line that starts with: Defaults env_reset # Or look for the secure_path line
Modify or add the vagrant user exception
# Add this line AFTER the Defaults section: Defaults:vagrant !requiretty Defaults:vagrant env_keep += "PATH" # Or modify the existing vagrant line to: # If you see: %vagrant ALL=(ALL) NOPASSWD:ALL # Change it to: vagrant ALL=(ALL) NOPASSWD:ALL Defaults:vagrant !requiretty, !env_reset # Save and exit: # In visudo (vim): Press Esc, then type :wq and press Enter
Alternative: Simplify vagrant sudoers entry
sudo sh -c 'echo "vagrant ALL=(ALL) NOPASSWD: ALL" > /etc/sudoers.d/vagrant' sudo chmod 0440 /etc/sudoers.d/vagrant # Breakdown: # Creates a dedicated sudoers file for vagrant user # Gives vagrant passwordless sudo access # Sets correct permissions (0440 = readable by owner and group)
Test sudo without warnings
sudo whoami # Should output: root # WITHOUT any warnings or error messages
root
Exit the VM
exit
From Mac: Re-run Ansible ping to verify clean output
ansible all -m ping
postgresdb | SUCCESS => { "ansible_facts": { "discovered_interpreter_python": "/usr/bin/python3" }, "changed": false, "ping": "pong" } ✨ No warnings! Clean output!

💡 Understanding the Fixes

  • /etc/hosts fix - Ensures the hostname resolves to localhost, preventing DNS lookup warnings
  • visudo - Safely edits sudo configuration with syntax checking
  • !requiretty - Allows sudo to work without a terminal (needed for Ansible)
  • NOPASSWD - Vagrant users don't need to enter password for sudo
  • 0440 permissions - Sudoers files must have strict permissions for security
  • These are one-time fixes - you won't need to repeat them

💡 Pro Tip: Ansible Output

After these fixes, your Ansible playbook runs will have clean, professional output without warning messages cluttering the logs.

🔒 Security Note

NOPASSWD sudo is convenient for development VMs but should be carefully considered in production environments. Use it only for trusted automation users.

🎯 Production Alternative

In production, consider using Ansible Vault to securely store sudo passwords instead of NOPASSWD configurations.
