What is RBAC?

Role-Based Access Control (RBAC) is a security paradigm where access permissions are assigned to roles rather than individual users.

🎭 The Core Concept

User
→
Role
→
Privileges
💡 Key Insight: Instead of saying "John can read the employees table", we say "Analysts can read the employees table, and John is an Analyst."

Why RBAC?

📦 Scalability

Manage 1000 users by controlling 10 roles instead of 1000 individual permission sets

🔄 Maintainability

Change one role's permissions to update all users in that role instantly

🎯 Clarity

Job functions are clearly mapped to database access patterns

🛡️ Security

Enforce least-privilege principle systematically across your organization

Traditional vs RBAC Approach

❌ Traditional (Direct Assignment) ✅ RBAC (Role-Based)

PostgreSQL RBAC Architecture

PostgreSQL implements RBAC through a multi-layered privilege system with cluster-wide roles and object-level permissions.

🏛️ The Three-Tier Pyramid

Tier 3: Object Privileges
Tables, Views, Functions, Sequences
Tier 2: Role Hierarchy
Group Roles (readonly, admin, etc.)
Tier 1: User Accounts
Login Roles (Humans & Applications)
✅ Design Pattern: Assign privileges bottom-up (Objects → Roles → Users). Each layer abstracts the complexity of the one below it.

📊 Privilege Control Layers

Layer Controls Examples
Cluster Login, create databases, manage roles LOGIN, CREATEDB, CREATEROLE
Database Connect, create schemas CONNECT, CREATE
Schema Use schema, create objects USAGE, CREATE
Table CRUD operations SELECT, INSERT, UPDATE, DELETE
Function Execute procedures EXECUTE
Row/Column Fine-grained data access RLS Policies, Column-level GRANTs
-- Example: Multi-layer privilege structure -- Layer 1: Cluster-level CREATE ROLE developer LOGIN PASSWORD 'dev123'; -- Layer 2: Database-level GRANT CONNECT ON DATABASE myapp TO developer; -- Layer 3: Schema-level GRANT USAGE ON SCHEMA public TO developer; -- Layer 4: Table-level GRANT SELECT, INSERT ON employees TO developer;

Role Hierarchy in Action

PostgreSQL roles can inherit privileges from other roles, creating a powerful inheritance tree that mirrors your organizational structure.

🌳 Enterprise Role Tree

🔴 SUPERUSER (postgres)
Full control - bypasses all checks
🟣 app_admin
Schema management, grant permissions
🔵 readwrite_user
SELECT, INSERT, UPDATE, DELETE
🟢 readonly_user
SELECT only
⚠️ Critical: Roles with INHERIT attribute (default) automatically gain privileges from parent roles. Roles with NOINHERIT must explicitly use SET ROLE to access parent privileges.
-- Step 1: Create group roles (no login) CREATE ROLE readonly NOLOGIN; CREATE ROLE readwrite NOLOGIN; CREATE ROLE app_admin NOLOGIN; -- Step 2: Build inheritance chain GRANT readonly TO readwrite; GRANT readwrite TO app_admin; -- Step 3: Grant object privileges to base role GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly; GRANT INSERT, UPDATE, DELETE ON ALL TABLES IN SCHEMA public TO readwrite; -- Step 4: Create user accounts and assign roles CREATE USER alice PASSWORD 'Alice@123'; CREATE USER bob PASSWORD 'Bob@123'; GRANT readonly TO alice; GRANT readwrite TO bob; -- Result: Alice can SELECT, Bob can SELECT + INSERT/UPDATE/DELETE
💡 Pro Tip: Always use NOLOGIN for group roles and LOGIN for actual user accounts. This separation makes your security model crystal clear.

🔍 Viewing Role Memberships

-- List all roles \du -- Query role memberships SELECT roleid::regrole AS role, member::regrole AS member FROM pg_auth_members; -- Check what roles a user belongs to SELECT rolname FROM pg_roles WHERE pg_has_role('alice', oid, 'member');

Privilege Types & Scopes

PostgreSQL offers granular control from cluster-wide attributes down to individual columns in tables. This enables enterprises to align database security with corporate access policies, ensuring every role has only the rights it needs.

🎛️ Role Attributes (Cluster-Level)

LOGIN

Allows the role to connect to PostgreSQL. Required for any user or application account.

SUPERUSER

Bypasses ALL permission checks. Use extremely sparingly - only for DBAs.

CREATEDB

Can create new databases. Useful for dev leads or testing environments.

CREATEROLE

Can create, alter, and drop other roles. Delegated admin capability.

REPLICATION

Can initiate streaming replication. Required for replica servers.

BYPASSRLS

Bypasses Row-Level Security policies. Dangerous - use carefully.

🧩 Practical SQL Examples

-- Database privileges GRANT CONNECT ON DATABASE analytics TO analyst; GRANT CREATE ON DATABASE analytics TO dev_team; -- Schema privileges GRANT USAGE ON SCHEMA finance TO readonly; GRANT CREATE ON SCHEMA finance TO finance_admin; -- Table privileges GRANT SELECT, INSERT, UPDATE ON employees TO dev_team; REVOKE DELETE ON employees FROM dev_team; -- Column-level privileges (GDPR/HIPAA compliance) GRANT SELECT (name, email) ON employees TO customer_service; REVOKE SELECT (salary, ssn) ON employees FROM customer_service; -- Function privileges GRANT EXECUTE ON FUNCTION calculate_bonus(int) TO finance_user; -- Grant on ALL existing objects GRANT SELECT ON ALL TABLES IN SCHEMA public TO readonly; -- Grant on ALL future objects (critical!) ALTER DEFAULT PRIVILEGES IN SCHEMA public GRANT SELECT ON TABLES TO readonly;

🔄 Privilege Inheritance Flow

Admin Role
GRANT CREATE, GRANT privileges
Read/Write Role
SELECT, INSERT, UPDATE, DELETE
Read-Only Role
SELECT
💡 Concept: Privileges flow downward through inheritance chains. When a higher role (like readwrite) includes another (readonly), all permissions are accumulated — simplifying management for corporate teams.

🧠 Deep Dive: Default Privileges & Ownership

  • Ownership: The creator (owner) of an object automatically receives all privileges on it.
  • Grant Chain: Only the grantor or a superuser can revoke privileges.
  • Default Privileges: Future objects inherit the privileges you define via ALTER DEFAULT PRIVILEGES.
  • Auditing: Use pg_roles, pg_shdepend, and pg_auth_members to monitor assignments.

🧠 Advanced RBAC Concepts

PostgreSQL goes beyond standard role inheritance. It introduces powerful tools for fine-grained data security, automation, and compliance alignment.

🔍 Ownership Rule: The owner of a database object automatically has all privileges on it. Privileges granted by others can only be revoked by the grantor or superuser.

🔒 Row-Level Security (RLS)

RLS enables per-row data filtering based on user identity, ensuring corporate compliance (GDPR, HIPAA, SOC2).

-- Enable Row-Level Security ALTER TABLE employees ENABLE ROW LEVEL SECURITY; -- Define Policy (only view own data) CREATE POLICY employee_isolation ON employees USING (username = current_user); -- Apply Policy ALTER TABLE employees FORCE ROW LEVEL SECURITY;
⚠️ Compliance Tip: RLS is a must-have for corporate environments handling PII or multi-tenant data.

⚙️ Default Privileges (Automating Grants)

-- Auto-grant SELECT on future tables ALTER DEFAULT PRIVILEGES IN SCHEMA analytics GRANT SELECT ON TABLES TO readonly; -- Auto-grant EXECUTE on new functions ALTER DEFAULT PRIVILEGES IN SCHEMA finance GRANT EXECUTE ON FUNCTIONS TO finance_team;
✅ Corporate Use: Reduces human error by automating permission consistency across large teams.
