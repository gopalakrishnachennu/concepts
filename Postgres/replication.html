💾 Concept #5 — WAL Archiving & Point-in-Time Recovery (PITR)

🧠 Core Concept

WAL (Write-Ahead Log) records every database change. By archiving WAL files + base backups, you can restore to ANY exact moment—even seconds before disaster.

WAL ARCHIVING FLOW
Active DB
📝 Writing WAL
Archive Storage
💾 S3 / NAS
Recovery Node
🔄 PITR Restore

📊 Timeline Visualization

10:00 AM
Base Backup
11:00 AM
WAL 0001
11:37 AM
❌ Accident
11:35 AM
✅ Recovery Point

Recovery Strategy: Restore base backup (10:00) + replay WAL until 11:35 (2 minutes before accident)

⚙️ How It Works

1️⃣ Normal Operation

WAL segments archive continuously

→

2️⃣ Disaster Strikes

DROP TABLE or corruption

→

3️⃣ Restore Base Backup

Last nightly snapshot

→

4️⃣ Replay WALs

Until target timestamp

# Enable Archiving (postgresql.conf) archive_mode = on archive_command = 'test ! -f /mnt/backup/%f && cp %p /mnt/backup/%f' archive_timeout = 60 wal_level = replica # Take Base Backup pg_basebackup -D /mnt/backup/base_2025_10_24 -Ft -z -P # Restore Configuration (postgresql.auto.conf) restore_command = 'cp /mnt/backup/%f %p' recovery_target_time = '2025-10-24 11:35:00' # Start Recovery touch recovery.signal systemctl start postgresql

🧪 Recovery Scenarios

Scenario Recovery Method Expected Result
Power Failure Latest WAL replay Recover to last transaction
DROP TABLE PITR to 5 min before Table restored intact
Disk Corruption Restore on new host + WAL Full database rebuilt
Ransomware PITR before infection Clean state recovered

🧰 pgBackRest Integration

# pgbackrest.conf [db] pg1-path=/var/lib/postgresql/16/main [global] repo1-path=/mnt/backup repo1-retention-full=7 start-fast=y compress-level=3 # Commands pgbackrest stanza-create pgbackrest backup --type=full pgbackrest backup --type=diff pgbackrest restore --type=time "--target=2025-10-24 11:35:00"
⚠️ Common Pitfalls:

• WAL disk fills: archive_command failing → add monitoring alerts

• Wrong recovery time: Clock skew or timezone issues → use UTC

• No restore tests: False sense of security → automate monthly PITR drills

• Archive corruption: Manual copy errors → use checksums or pgBackRest

🧬 Concept #2 — Logical Replication

🧠 What Makes It Different

Instead of copying binary WAL files, logical replication decodes changes into table-level operations (INSERT/UPDATE/DELETE) and sends only those.

Publisher
📤 Decoding WAL
Subscriber
📥 Applying SQL

1️⃣ Publication

Define which tables to replicate

→

2️⃣ WAL Decoding

Binary WAL → SQL statements

→

3️⃣ Stream

Send row changes only

→

4️⃣ Subscription

Apply changes to target DB

🔬 Step-by-Step Flow

📤
Publisher Creates Publication CREATE PUBLICATION pub_orders FOR TABLE orders;
📥
Subscriber Connects CREATE SUBSCRIPTION sub_orders CONNECTION '...';
📋
Initial Data Copy

COPY existing table data

🔄
Continuous Sync

Stream live INSERT/UPDATE/DELETE

Feature Streaming Logical
Level Physical (cluster) Logical (table)
Cross-version? ❌ No ✅ Yes
Partial tables? ❌ No ✅ Yes
Bidirectional? ❌ No ✅ Possible
Performance Faster Slower

🏢 Real Corporate Use Cases

🏦 Banking Example

Replicate only transactions table from 50 branch DBs to HQ analytics server. No need for entire database replication.

🛒 E-commerce Split

Monolith → Microservices: Product service subscribes to products, Order service to orders.

-- Publisher Setup CREATE PUBLICATION pub_orders FOR TABLE orders; -- Subscriber Setup CREATE SUBSCRIPTION sub_orders CONNECTION 'host=192.168.1.10 dbname=sales user=rep_user' PUBLICATION pub_orders; -- Monitor SELECT * FROM pg_stat_subscription;
⚠️ Common Pitfalls:

• DDL (schema changes) are NOT replicated automatically

• Replication slots can cause disk bloat if subscriber offline

• Conflicts on dual writes require careful design

🔥 Concept #3 — Hot Standby & Read Replicas

🧠 Core Concept

A Hot Standby is a replica that continuously receives WALs, replays them, AND serves read-only queries simultaneously.

⚡ Query Conflicts Deep Dive

QUERY CONFLICT SCENARIO
Primary
🔄 DELETE rows

Generates WAL

Standby
📖 Long SELECT

Reading same rows

Standby must replay DELETE, but user query is still reading those rows!

⚠️ CONFLICT DETECTED

Option 1: Cancel the SELECT query

Option 2: Delay WAL replay

Configured by: max_standby_streaming_delay = 30s

If delay < 30s

PostgreSQL waits for query

If delay > 30s

Cancels query, applies WAL

# Hot Standby Configuration hot_standby = on max_standby_streaming_delay = 30s # How long to delay WAL replay hot_standby_feedback = on # Tell primary about queries # Monitor Query Conflicts SELECT * FROM pg_stat_database_conflicts;

📊 Monitoring Queries

hot_standby_feedback: Prevents conflicts by signaling primary
