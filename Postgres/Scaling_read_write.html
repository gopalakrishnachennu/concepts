PostgreSQL Scaling Fundamentals

Two Main Scaling Approaches:

🔼 Vertical Scaling (Scale Up)

Definition: Adding more power to your existing server (CPU, RAM, Disk)

  • Pros: Simple to implement, no code changes, maintains ACID properties
  • Cons: Hardware limits, single point of failure, expensive at scale
  • When to use: Small to medium applications, when consistency is critical

↔️ Horizontal Scaling (Scale Out)

Definition: Adding more servers to distribute the load

  • Pros: Unlimited scalability, high availability, cost-effective
  • Cons: Complex setup, potential consistency issues, requires application changes
  • When to use: Large applications, high read loads, need for high availability

Horizontal Scaling Types:

Type Description Use Case Consistency
Synchronous Replication Primary waits for replica to confirm write before committing Banking, financial systems Strong consistency
Asynchronous Replication Primary commits immediately, replica updates later Social media, analytics, blogs Eventual consistency

Synchronous Replication Configuration:

# postgresql.conf on PRIMARY synchronous_commit = on synchronous_standby_names = 'replica_1,replica_2' # Options for synchronous_standby_names: # FIRST 1 (replica_1, replica_2) - Wait for any 1 replica # ANY 2 (replica_1, replica_2, replica_3) - Wait for any 2 replicas # replica_1 - Wait specifically for replica_1

Comparison Table:

Aspect Synchronous Asynchronous
Data Safety ✅ Zero data loss ⚠️ Possible data loss (seconds/minutes)
Performance ⚠️ Slower writes (wait for confirmation) ✅ Faster writes
Network Sensitivity ❌ High - network lag affects writes ✅ Low - writes not affected
Consistency ✅ Strong consistency ⚠️ Eventual consistency
Use Cases Banking, financial transactions, legal records Social media, blogs, analytics, caching

⚠️ Important Considerations:

Synchronous Replication: If the replica goes down, writes will FAIL or BLOCK until timeout. Always have multiple replicas or use FIRST/ANY syntax.

Asynchronous Replication: In case of primary failure before replication, recent transactions (last few seconds) may be lost.

🔥 What is Hot Standby?

Hot Standby allows read-only queries on a standby replica while it's continuously receiving updates from the primary. This enables:

  • ✅ Offload read traffic from primary to replicas
  • ✅ Serve read requests even during primary maintenance
  • ✅ Quick failover - standby can become primary in seconds
  • ⚠️ Eventually consistent - replicas may lag behind primary by milliseconds to seconds

Hot Standby Configuration:

# PRIMARY postgresql.conf wal_level = replica max_wal_senders = 5 wal_keep_size = 1GB hot_standby = on hot_standby_feedback = on # Prevents query conflicts # STANDBY postgresql.conf hot_standby = on max_standby_streaming_delay = 30s # How long to wait before canceling conflicting queries wal_receiver_status_interval = 10s

Monitoring Hot Standby Lag:

# On PRIMARY - Check replication lag for each replica SELECT application_name, client_addr, state, sync_state, pg_wal_lsn_diff(pg_current_wal_lsn(), replay_lsn) AS byte_lag, EXTRACT(EPOCH FROM (now() - reply_time)) AS seconds_since_last_reply FROM pg_stat_replication; # On STANDBY - Check current lag SELECT now() - pg_last_xact_replay_timestamp() AS replication_lag; # Check if standby is accepting read queries SELECT pg_is_in_recovery(); -- Should be 't' SHOW hot_standby; -- Should be 'on'

✅ Real-World Best Practices for Hot Standby:

  • Application-Level Routing: Use connection poolers (PgBouncer, HAProxy) to route writes to primary and reads to standbys
  • Monitor Lag: Set up alerts when replication lag exceeds acceptable threshold (typically 5-10 seconds)
  • Handle Query Conflicts: Long-running queries on standby may be canceled if they conflict with incoming WAL. Design queries accordingly
  • Use Replication Slots: Prevents WAL deletion before standby processes it

🌐 What is Multi-Master Replication?

Multi-Master (also called Multi-Primary) allows writes on multiple database nodes simultaneously. Each master accepts writes and propagates changes to other masters.

Technologies for PostgreSQL Multi-Master:
  • BDR (Bi-Directional Replication): By EDB/2ndQuadrant - enterprise solution
  • Logical Replication: Built into PostgreSQL 10+ (limited multi-master capabilities)
  • Bucardo: Trigger-based multi-master replication
  • Pgpool-II: Connection pooling with limited multi-master support

Logical Replication Setup (PostgreSQL 10+):

# ============================================ # PUBLISHER NODE (Master 1) SETUP # ============================================ # 1. Enable logical replication in postgresql.conf wal_level = logical max_replication_slots = 10 max_wal_senders = 10 # 2. Restart PostgreSQL sudo systemctl restart postgresql # 3. Create a publication for specific tables CREATE PUBLICATION my_publication FOR TABLE users, orders, products; # Or for all tables in the database CREATE PUBLICATION all_tables FOR ALL TABLES; # 4. Create replication user CREATE ROLE replicator WITH REPLICATION LOGIN PASSWORD 'secure_pass'; GRANT SELECT ON ALL TABLES IN SCHEMA public TO replicator; # 5. Edit pg_hba.conf to allow logical replication host all replicator subscriber_ip/32 md5 # ============================================ # SUBSCRIBER NODE (Master 2) SETUP # ============================================ # 1. Create the same table structures as publisher CREATE TABLE users ( id SERIAL PRIMARY KEY, username VARCHAR(50), email VARCHAR(100) ); # 2. Create a subscription CREATE SUBSCRIPTION my_subscription CONNECTION 'host=publisher_ip port=5432 dbname=mydb user=replicator password=secure_pass' PUBLICATION my_publication; # 3. Verify subscription is working SELECT * FROM pg_stat_subscription; # ============================================ # BIDIRECTIONAL SETUP (True Multi-Master) # ============================================ # On Master 1: Create publication AND subscription to Master 2 CREATE PUBLICATION pub_master1 FOR ALL TABLES; CREATE SUBSCRIPTION sub_from_master2 CONNECTION 'host=master2_ip dbname=mydb user=replicator password=pass' PUBLICATION pub_master2; # On Master 2: Create publication AND subscription to Master 1 CREATE PUBLICATION pub_master2 FOR ALL TABLES; CREATE SUBSCRIPTION sub_from_master1 CONNECTION 'host=master1_ip dbname=mydb user=replicator password=pass' PUBLICATION pub_master1;

Monitoring Logical Replication:

# Check publication status SELECT * FROM pg_publication; SELECT * FROM pg_publication_tables; # Check subscription status SELECT subname, pid, received_lsn, latest_end_lsn, last_msg_send_time, last_msg_receipt_time, latest_end_time FROM pg_stat_subscription; # Check replication slots SELECT slot_name, plugin, slot_type, database, active, restart_lsn FROM pg_replication_slots; # View subscription workers SELECT * FROM pg_stat_subscription_stats;

⚠️ Multi-Master Challenges & Solutions:

1. Conflict Resolution:

Problem: Two masters update the same row simultaneously

Solutions:

  • Last Write Wins: Most recent timestamp wins (default in BDR)
  • First Write Wins: First committed transaction wins
  • Application-Level: Use UUIDs, partition data by region
  • Custom Functions: Define conflict resolution functions
2. Circular Replication Prevention:

PostgreSQL logical replication automatically prevents loops by tracking origin of changes

3. Schema Changes:

DDL changes (ALTER TABLE, etc.) are NOT replicated automatically. Must be applied manually to all masters.

# Handling conflicts - Check for conflicts in logs SELECT * FROM pg_stat_subscription WHERE last_msg_send_time != last_msg_receipt_time; # For BDR (Enterprise) - Conflict detection SELECT conflict_time, conflict_type, conflict_resolution, local_tuple, remote_tuple FROM bdr.conflict_history ORDER BY conflict_time DESC LIMIT 10;

Real-World Scenarios & Best Practices

🏆 Most Widely Used Method: Streaming Replication (Primary + Hot Standby)

Why it's popular:

  • ✅ Built into PostgreSQL (no external tools)
  • ✅ Easy to setup and maintain
  • ✅ Reliable and battle-tested
  • ✅ Works for 90% of use cases
  • ✅ Good balance of performance and data safety

Typical Setup:

  • 1 Primary (master) for writes
  • 2-3 Asynchronous Hot Standby replicas for reads
  • Application routes writes to primary, reads to replicas via connection pooler

🎯 Real-World Architecture Examples:

Scenario 1: E-Commerce Platform (100K daily users)

Architecture:

  • Primary: 1x (8 vCPU, 32GB RAM) - Handles all writes
  • Read Replicas: 3x (4 vCPU, 16GB RAM) - Distributed across availability zones
  • Replication: Asynchronous streaming
  • Load Balancer: HAProxy routes reads to replicas round-robin

Configuration:

# Primary - postgresql.conf max_connections = 200 shared_buffers = 8GB effective_cache_size = 24GB work_mem = 40MB maintenance_work_mem = 2GB wal_level = replica max_wal_senders = 5 synchronous_commit = off # For better write performance

Results:

  • Write capacity: ~5,000 TPS
  • Read capacity: ~15,000 TPS (distributed across replicas)
  • Average replication lag: < 500ms

Scenario 2: Financial Application (Banking)

Architecture:

  • Primary: 1x (16 vCPU, 64GB RAM)
  • Synchronous Replica: 1x (same specs) - Zero data loss
  • Asynchronous Replicas: 2x for reporting/analytics
  • Replication: Synchronous to 1 replica, async to others

Configuration:

# Primary - postgresql.conf synchronous_commit = on synchronous_standby_names = 'FIRST 1 (replica_sync)' fsync = on full_page_writes = on wal_log_hints = on

Trade-offs:

  • ✅ Zero data loss guarantee
  • ✅ Immediate failover capability
  • ⚠️ ~20% slower writes due to sync wait
  • ⚠️ Network latency directly impacts write performance

Scenario 3: Global SaaS Application

Architecture:

  • Multi-Region: 3 regions (US, EU, APAC)
  • Each Region: 1 Primary + 2 Read Replicas
  • Cross-Region: Logical replication between primaries
  • Data Partitioning: By customer/tenant region

Setup:

# US Primary publishes to EU & APAC CREATE PUBLICATION us_pub FOR TABLE users WHERE (region = 'US'); # EU Primary subscribes to US data and publishes own CREATE SUBSCRIPTION from_us CONNECTION 'host=us-primary...' PUBLICATION us_pub; CREATE PUBLICATION eu_pub FOR TABLE users WHERE (region = 'EU');

Benefits:

  • ✅ Low latency for users in each region
  • ✅ Disaster recovery across regions
  • ✅ Compliance with data residency requirements
  • ⚠️ Eventual consistency across regions

📋 Step-by-Step Production Setup Checklist:

Pre-Deployment Checklist:

  1. ✅ Hardware/Cloud Resources: Provision servers with SSD storage
  2. ✅ Network: Ensure low-latency connection between primary and replicas (< 5ms ping)
  3. ✅ Security: Configure firewall rules, SSL/TLS for replication connections
  4. ✅ Monitoring: Set up Prometheus, Grafana, or CloudWatch
  5. ✅ Backup Strategy: Configure pg_basebackup, WAL archiving to S3/Azure/GCS
  6. ✅ Alerting: Configure alerts for lag > 10s, disk > 80%, connections > 80%
  7. ✅ Documentation: Document failover procedures
  8. ✅ Testing: Test failover process in staging

Sharding & Partitioning

🔪 What is Sharding vs Partitioning?

Partitioning (Single Database):

Definition: Splitting a large table into smaller pieces (partitions) within the SAME database server.

  • ✅ Built into PostgreSQL 10+
  • ✅ Transparent to applications
  • ✅ Improves query performance for large tables
  • ✅ Easier maintenance (drop old partitions)
  • ⚠️ Still limited by single server resources
Sharding (Multiple Databases):

Definition: Distributing data across MULTIPLE database servers, each holding a subset of data.

  • ✅ True horizontal scaling - unlimited capacity
  • ✅ Each shard operates independently
  • ⚠️ Complex application logic required
  • ⚠️ Difficult to maintain data integrity across shards
  • ⚠️ No built-in solution in PostgreSQL (requires Citus extension or app-level)

Partitioning Types in PostgreSQL:

Type Description Use Case Example
Range Partitioning Partition by value ranges Time-series data, dates Sales by year, logs by month
List Partitioning Partition by specific values Categorical data Users by country, orders by status
Hash Partitioning Partition by hash of column Even distribution Users by ID hash, random distribution

1. Range Partitioning Example:

-- Create parent table CREATE TABLE sales ( id SERIAL, sale_date DATE NOT NULL, amount NUMERIC(10,2), product_id INT ) PARTITION BY RANGE (sale_date); -- Create partitions for each year CREATE TABLE sales_2022 PARTITION OF sales FOR VALUES FROM ('2022-01-01') TO ('2023-01-01'); CREATE TABLE sales_2023 PARTITION OF sales FOR VALUES FROM ('2023-01-01') TO ('2024-01-01'); CREATE TABLE sales_2024 PARTITION OF sales FOR VALUES FROM ('2024-01-01') TO ('2025-01-01'); -- Create indexes on partitions CREATE INDEX idx_sales_2024_date ON sales_2024(sale_date); CREATE INDEX idx_sales_2024_product ON sales_2024(product_id); -- Queries automatically use correct partition SELECT * FROM sales WHERE sale_date = '2024-06-15'; -- PostgreSQL automatically queries only sales_2024 partition -- Drop old partitions easily (for data retention) DROP TABLE sales_2022;

2. List Partitioning Example:

-- Create parent table CREATE TABLE users ( id SERIAL, username VARCHAR(50), email VARCHAR(100), country VARCHAR(2) NOT NULL ) PARTITION BY LIST (country); -- Create partitions by country CREATE TABLE users_us PARTITION OF users FOR VALUES IN ('US'); CREATE TABLE users_eu PARTITION OF users FOR VALUES IN ('GB', 'DE', 'FR', 'ES', 'IT'); CREATE TABLE users_asia PARTITION OF users FOR VALUES IN ('JP', 'CN', 'IN', 'KR'); CREATE TABLE users_other PARTITION OF users DEFAULT; -- Insert automatically goes to correct partition INSERT INTO users (username, email, country) VALUES ('john', 'john@example.com', 'US'); -- Goes to users_us partition

3. Hash Partitioning Example:

-- Create parent table CREATE TABLE orders ( id SERIAL, user_id INT NOT NULL, order_date DATE, total NUMERIC(10,2) ) PARTITION BY HASH (user_id); -- Create 4 hash partitions CREATE TABLE orders_p0 PARTITION OF orders FOR VALUES WITH (MODULUS 4, REMAINDER 0); CREATE TABLE orders_p1 PARTITION OF orders FOR VALUES WITH (MODULUS 4, REMAINDER 1); CREATE TABLE orders_p2 PARTITION OF orders FOR VALUES WITH (MODULUS 4, REMAINDER 2); CREATE TABLE orders_p3 PARTITION OF orders FOR VALUES WITH (MODULUS 4, REMAINDER 3); -- Data is automatically distributed evenly INSERT INTO orders (user_id, order_date, total) VALUES (12345, '2024-01-01', 99.99); -- PostgreSQL calculates hash(12345) % 4 to determine partition

Sharding with Citus (PostgreSQL Extension):

-- Install Citus extension CREATE EXTENSION citus; -- Add worker nodes (shards) SELECT citus_add_node('worker1.example.com', 5432); SELECT citus_add_node('worker2.example.com', 5432); SELECT citus_add_node('worker3.example.com', 5432); -- Create distributed table (sharded across workers) CREATE TABLE events ( user_id BIGINT, event_type TEXT, event_time TIMESTAMP, properties JSONB ); SELECT create_distributed_table('events', 'user_id'); -- Queries are automatically distributed to shards SELECT user_id, COUNT(*) FROM events WHERE event_time > '2024-01-01' GROUP BY user_id; -- Citus pushes query to all worker nodes and aggregates results -- Check shard distribution SELECT * FROM citus_shards;

Application-Level Sharding Pattern:

# Python example: Routing to correct shard import hashlib import psycopg2 class ShardManager: def __init__(self): self.shards = [ {'host': 'shard1.db.com', 'db': 'shard1'}, {'host': 'shard2.db.com', 'db': 'shard2'}, {'host': 'shard3.db.com', 'db': 'shard3'}, {'host': 'shard4.db.com', 'db': 'shard4'} ] def get_shard(self, user_id): # Hash user_id and determine shard hash_val = int(hashlib.md5(str(user_id).encode()).hexdigest(), 16) shard_num = hash_val % len(self.shards) return self.shards[shard_num] def execute_query(self, user_id, query): shard = self.get_shard(user_id) conn = psycopg2.connect( host=shard['host'], database=shard['db'], user='app_user', password='password' ) cur = conn.cursor() cur.execute(query) result = cur.fetchall() conn.close() return result # Usage manager = ShardManager() results = manager.execute_query( user_id=12345, query="SELECT * FROM orders WHERE user_id = 12345" )

⚠️ Sharding Challenges:

  • Cross-Shard Queries: JOINs across shards are slow/impossible
  • Rebalancing: Adding/removing shards requires data migration
  • Transactions: Distributed transactions are complex (2PC)
  • Backup/Restore: Must coordinate across all shards
  • Hot Shards: Uneven data distribution can cause bottlenecks
Solutions:
  • Use consistent hashing for easier rebalancing
  • Denormalize data to avoid cross-shard queries
  • Use shard-local transactions when possible
  • Monitor shard sizes and rebalance proactively

Foreign Data Wrappers (FDW)

🌉 What are Foreign Data Wrappers?

Definition: FDW allows PostgreSQL to query external data sources (other PostgreSQL servers, MySQL, Oracle, MongoDB, CSV files, APIs) as if they were local tables.

Key Benefits:
  • ✅ Query data from multiple databases in a single SQL query
  • ✅ No ETL needed - query data in real-time
  • ✅ Migrate data gradually from legacy systems
  • ✅ Build federated database systems
  • ✅ Access non-PostgreSQL data sources
Common FDW Extensions:
  • postgres_fdw: Connect to other PostgreSQL servers
  • mysql_fdw: Connect to MySQL/MariaDB
  • oracle_fdw: Connect to Oracle databases
  • mongo_fdw: Connect to MongoDB
  • file_fdw: Read CSV/text files
  • multicorn: Write custom FDW in Python

1. postgres_fdw - Connect to Remote PostgreSQL:

-- Step 1: Install extension on local database CREATE EXTENSION postgres_fdw; -- Step 2: Create server connection CREATE SERVER remote_db FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host 'remote-server.com', port '5432', dbname 'remote_database'); -- Step 3: Create user mapping CREATE USER MAPPING FOR local_user SERVER remote_db OPTIONS (user 'remote_user', password 'remote_password'); -- Step 4: Import foreign schema (all tables) IMPORT FOREIGN SCHEMA public FROM SERVER remote_db INTO public; -- OR create specific foreign tables manually CREATE FOREIGN TABLE remote_orders ( order_id INT, user_id INT, amount NUMERIC, order_date DATE ) SERVER remote_db OPTIONS (schema_name 'public', table_name 'orders'); -- Step 5: Query remote data like local tables SELECT * FROM remote_orders WHERE order_date > '2024-01-01'; -- Join local and remote tables SELECT local_users.name, remote_orders.amount FROM local_users JOIN remote_orders ON local_users.id = remote_orders.user_id; -- Check FDW performance EXPLAIN ANALYZE SELECT * FROM remote_orders WHERE user_id = 123;

2. file_fdw - Query CSV Files:

-- Install extension CREATE EXTENSION file_fdw; -- Create server CREATE SERVER file_server FOREIGN DATA WRAPPER file_fdw; -- Create foreign table pointing to CSV CREATE FOREIGN TABLE sales_csv ( sale_date DATE, product TEXT, amount NUMERIC ) SERVER file_server OPTIONS (filename '/var/data/sales.csv', format 'csv', header 'true'); -- Query CSV as a table SELECT product, SUM(amount) FROM sales_csv GROUP BY product; -- Join CSV with database table SELECT p.product_name, s.amount FROM products p JOIN sales_csv s ON p.product_name = s.product;

3. mysql_fdw - Connect to MySQL:

-- Install extension (requires mysql_fdw package) CREATE EXTENSION mysql_fdw; -- Create server CREATE SERVER mysql_server FOREIGN DATA WRAPPER mysql_fdw OPTIONS (host 'mysql-host.com', port '3306'); -- User mapping CREATE USER MAPPING FOR postgres SERVER mysql_server OPTIONS (username 'mysql_user', password 'mysql_pass'); -- Create foreign table CREATE FOREIGN TABLE mysql_customers ( id INT, name VARCHAR(100), email VARCHAR(100) ) SERVER mysql_server OPTIONS (dbname 'crm', table_name 'customers'); -- Query MySQL from PostgreSQL SELECT * FROM mysql_customers WHERE id > 1000;

Real-World Use Case: Data Federation

/* Scenario: E-commerce company with: - Orders DB (PostgreSQL) - Customers DB (MySQL legacy system) - Product Analytics (CSV exports) - Want to create unified reports without ETL */ -- Setup FDWs for all sources CREATE EXTENSION postgres_fdw; CREATE EXTENSION mysql_fdw; CREATE EXTENSION file_fdw; -- Connect to remote PostgreSQL orders DB CREATE SERVER orders_db FOREIGN DATA WRAPPER postgres_fdw OPTIONS (host 'orders.db.internal', dbname 'orders'); CREATE USER MAPPING FOR current_user SERVER orders_db OPTIONS (user 'reporter', password 'pass'); CREATE FOREIGN TABLE remote_orders ( order_id INT, customer_id INT, total NUMERIC, order_date DATE ) SERVER orders_db OPTIONS (table_name 'orders'); -- Connect to MySQL customers DB CREATE SERVER mysql_crm FOREIGN DATA WRAPPER mysql_fdw OPTIONS (host 'mysql.legacy.internal', port '3306'); CREATE USER MAPPING FOR current_user SERVER mysql_crm OPTIONS (username 'analyst', password 'pass'); CREATE FOREIGN TABLE mysql_customers ( customer_id INT, customer_name VARCHAR, country VARCHAR ) SERVER mysql_crm OPTIONS (dbname 'crm', table_name 'customers'); -- Access CSV analytics CREATE SERVER csv_server FOREIGN DATA WRAPPER file_fdw; CREATE FOREIGN TABLE product_views ( product_id INT, views INT, date DATE ) SERVER csv_server OPTIONS (filename '/data/product_analytics.csv', format 'csv', header 'true'); -- Now create unified report with data from 3 sources! SELECT c.customer_name, c.country, COUNT(o.order_id) as total_orders, SUM(o.total) as revenue, AVG(pv.views) as avg_product_views FROM mysql_customers c LEFT JOIN remote_orders o ON c.customer_id = o.customer_id LEFT JOIN product_views pv ON pv.date = o.order_date WHERE o.order_date >= '2024-01-01' GROUP BY c.customer_name, c.country ORDER BY revenue DESC;

⚠️ FDW Performance Considerations:

  • Network Latency: Each query crosses the network - can be slow
  • Limited Push-Down: Not all WHERE clauses are pushed to remote server
  • No Transactions: Foreign tables don't support full ACID across servers
  • Authentication: Passwords stored in plain text (use connection service files)
Optimization Tips:
  • Use use_remote_estimate = true for better query planning
  • Create indexes on foreign servers
  • Use materialized views to cache foreign data locally
  • Limit JOIN complexity with foreign tables

Materialized Views with FDW (Caching):

-- Create materialized view from foreign table CREATE MATERIALIZED VIEW cached_remote_orders AS SELECT * FROM remote_orders WHERE order_date >= CURRENT_DATE - INTERVAL '30 days'; -- Create index on materialized view CREATE INDEX idx_cached_orders_date ON cached_remote_orders(order_date); -- Refresh cache daily (schedule with cron or pg_cron) REFRESH MATERIALIZED VIEW CONCURRENTLY cached_remote_orders; -- Query fast local cache instead of slow remote SELECT * FROM cached_remote_orders WHERE order_date = '2024-10-15';

PostgreSQL: Distributed vs Non-Distributed

📊 PostgreSQL is NOT a Distributed Database by Default

What this means:

  • 🔹 PostgreSQL is designed as a single-node RDBMS
  • 🔹 Each PostgreSQL instance operates independently
  • 🔹 There is NO automatic data distribution across nodes
  • 🔹 Replication is achieved through streaming (not native distribution)

Contrast with True Distributed Databases:

  • ✅ Cassandra, CockroachDB, MongoDB: Data automatically sharded and replicated across cluster
  • ✅ Coordination: Built-in consensus protocols (Raft, Paxos)
  • ✅ Fault Tolerance: Automatic failover without manual intervention
  • ⚠️ Trade-offs: Often sacrifice strong consistency for availability (CAP theorem)

Comparison Table: PostgreSQL vs Distributed Databases

Feature PostgreSQL (Non-Distributed) Distributed DB (e.g., CockroachDB, Cassandra)
Data Distribution ❌ Manual (replication, FDW, Citus) ✅ Automatic sharding across nodes
Consistency ✅ Strong ACID guarantees (single node) ⚠️ Often eventual consistency (tunable)
Failover ⚠️ Manual or with tools (Patroni, repmgr) ✅ Automatic (built-in consensus)
Scaling Writes ⚠️ Limited to single primary (unless multi-master) ✅ Writes distributed across nodes
Transactions ✅ Full ACID on single node ⚠️ Limited cross-shard transactions
SQL Support ✅ Full SQL standard ⚠️ Often limited SQL or NoSQL
Operational Complexity ⚠️ Medium (DBA needed for scaling) ✅ Low (auto-scaling, auto-rebalancing)
Best For Transactional apps, strong consistency, complex queries Massive scale, high availability, geo-distribution

Making PostgreSQL "Distributed" with Extensions:

Option 1: Citus Extension (By Microsoft)

What it does: Turns PostgreSQL into a distributed database

-- Install Citus CREATE EXTENSION citus; -- Add worker nodes SELECT citus_add_node('worker1', 5432); SELECT citus_add_node('worker2', 5432); -- Create distributed table CREATE TABLE events ( user_id BIGINT, event_type TEXT, created_at TIMESTAMP ); SELECT create_distributed_table('events', 'user_id'); -- Now data is automatically sharded across workers! INSERT INTO events VALUES (123, 'click', NOW()); -- Citus routes to correct worker based on hash(user_id) -- Queries run in parallel across workers SELECT user_id, COUNT(*) FROM events GROUP BY user_id;

Pros:

  • ✅ Automatic data sharding
  • ✅ Parallel query execution
  • ✅ Still PostgreSQL - full SQL support

Cons:

  • ⚠️ Requires Citus coordinator node
  • ⚠️ Limited cross-shard JOINs
  • ⚠️ Not true auto-failover (needs Patroni)

Option 2: Patroni + etcd (High Availability Cluster)

What it does: Automatic failover and cluster management

# Patroni configuration (patroni.yml) scope: postgres-cluster name: postgres-node1 restapi: listen: 0.0.0.0:8008 connect_address: node1:8008 etcd: hosts: etcd1:2379,etcd2:2379,etcd3:2379 bootstrap: dcs: ttl: 30 loop_wait: 10 retry_timeout: 10 maximum_lag_on_failover: 1048576 postgresql: use_pg_rewind: true parameters: wal_level: replica hot_standby: "on" max_wal_senders: 5 max_replication_slots: 5 postgresql: listen: 0.0.0.0:5432 connect_address: node1:5432 data_dir: /var/lib/postgresql/14/main authentication: replication: username: replicator password: repl_password superuser: username: postgres password: postgres_password # Start Patroni on each node patroni /etc/patroni.yml # Automatic failover - if primary dies, Patroni promotes standby!

Pros:

  • ✅ Automatic failover (seconds, not minutes)
  • ✅ No data loss with synchronous replication
  • ✅ RESTful API for monitoring

Option 3: Pgpool-II (Connection Pooling + Load Balancing)

What it does: Load balance reads, pool connections, automatic failover

# pgpool.conf backend_hostname0 = 'primary-db' backend_port0 = 5432 backend_weight0 = 1 backend_flag0 = 'ALLOW_TO_FAILOVER' backend_hostname1 = 'standby1-db' backend_port1 = 5432 backend_weight1 = 1 backend_flag1 = 'ALLOW_TO_FAILOVER' backend_hostname2 = 'standby2-db' backend_port2 = 5432 backend_weight2 = 1 backend_flag2 = 'ALLOW_TO_FAILOVER' load_balance_mode = on master_slave_mode = on master_slave_sub_mode = 'stream' # Applications connect to Pgpool, which routes queries psql -h pgpool-host -p 9999 -U myuser mydb

Responsibilities: DBA in Distributed vs Non-Distributed

Responsibility PostgreSQL (Non-Distributed) Distributed Database
Scaling Manual setup of replication, sharding logic Auto-scaling (add nodes via UI/API)
Failover Manual promotion or Patroni setup Automatic (built-in Raft/Paxos)
Backup pg_dump, WAL archiving, custom scripts Often automated by platform
Monitoring Custom (Prometheus, Grafana, pg_stat_*) Built-in dashboards
Data Distribution Manual (Citus, FDW, app-level sharding) Automatic sharding and rebalancing
Consistency Tuning Configure sync/async replication Tune consistency level (quorum reads/writes)
Schema Changes ALTER TABLE on each node (or via FDW) Often limited DDL or automatic propagation

When to Choose What?

Choose PostgreSQL (Non-Distributed) When:

  • ✅ Strong ACID guarantees are critical (finance, healthcare)
  • ✅ Complex JOINs and transactions across tables
  • ✅ Data size is manageable (< 1TB) or can be partitioned
  • ✅ You have experienced DBAs
  • ✅ Read replicas can handle 90% of read traffic
  • ✅ You need full SQL standard compliance

Choose Distributed Database When:

  • ✅ Need to scale beyond 10TB+ data
  • ✅ Write traffic cannot be handled by single primary
  • ✅ Geo-distributed deployment (multi-region)
  • ✅ Auto-scaling and auto-failover are priorities
  • ✅ Eventual consistency is acceptable
  • ✅ Minimal operational overhead desired

Hybrid Approach (Best of Both Worlds):

Many companies use:

  • PostgreSQL: For transactional data (orders, payments, user accounts)
  • Distributed DB (Cassandra/MongoDB): For logs, analytics, time-series data
  • Redis: For caching and session storage
  • Kafka: For event streaming between systems

Example Architecture:

  • Write to PostgreSQL (source of truth)
  • Stream changes via Debezium/Kafka to Cassandra
  • Query Cassandra for analytics at scale
  • Best of both: ACID + Scale
