🐘 PostgreSQL WAL Architecture

Write-Ahead Logging: How PostgreSQL Captures Only Changes

💡 Core Concept: Write-Ahead Logging (WAL)

PostgreSQL uses number">3. On COMMIT, backend forces WAL flush to disk - Calls XLogFlush(LSN) - Uses fsync() to ensure durability - Only after fsync returns, COMMIT is acknowledged 4. Checkpoint process writes dirty pages to disk - Records checkpoint LSN in WAL - Allows old WAL files to be recycled/archived

WAL Record Types

Heap Operations

  • INSERT - New row added
  • UPDATE - Row modified
  • DELETE - Row removed
  • HOT UPDATE - Heap-Only Tuple update

Index Operations

  • BTREE_INSERT - B-tree index entry
  • BTREE_SPLIT - Page split
  • BTREE_DELETE - Index cleanup

Transaction Control

  • XACT_COMMIT - Transaction commits
  • XACT_ABORT - Transaction rollback
  • CHECKPOINT - Checkpoint record

System Operations

  • XLOG_SWITCH - WAL file switch
  • BACKUP_START - Base backup begins
  • BACKUP_END - Base backup completes

⏰ Point-in-Time Recovery (PITR)

The killer feature of WAL: restore to ANY point in time!

-- Disaster strikes Tuesday at 14:35:00 - someone runs: DELETE FROM orders WHERE status = 'pending'; -- Oops! That deleted 50,000 orders without WHERE clause! -- RECOVERY PROCESS: 1. Stop PostgreSQL 2. Restore Sunday's base backup (500 GB) 3. Create recovery.conf: restore_command = 'cp /backup/wal/%f %p' recovery_target_time = '2024-11-26 14:34:59' // 1 second before disaster! recovery_target_action = 'promote' 4. Start PostgreSQL - Reads base backup - Applies Monday's WAL (all 15 GB) - Applies Tuesday's WAL up to 14:34:59 - Stops at exact moment before DELETE 5. Database promoted - back online with all 50,000 orders intact! // Time to recover: ~30 minutes // Alternative without WAL: Lose everything since Sunday (catastrophic!)

How PostgreSQL Replays WAL

1
Read Base Backup

Load data files from Sunday into memory

2
Find Starting LSN

Base backup contains checkpoint LSN: 0/A0000000

3
Read First WAL File

Open 00000001000000000000000A (Monday's first WAL)

4
Replay Each Record

For each WAL record:
- Read LSN and operation type
- Load affected data page
- Apply change (INSERT/UPDATE/DELETE)
- Advance to next LSN

5
Continue Through WAL Files

Automatically load next WAL segment when current completes

6
Stop at Target Time

When LSN timestamp reaches 14:34:59, stop replay and promote

🚀 Advanced WAL Concepts

Full Page Writes (FPW)

Why WAL Sometimes Contains Full Pages
After a CHECKPOINT, the first modification to each page writes the FULL page to WAL.

Why? Protect against torn pages (partial writes during crash)

Example:
- Checkpoint at LSN 0/A0000000
- First UPDATE to page 42 after checkpoint
- WAL record contains: FULL 8KB page + change details
- Subsequent UPDATEs to same page: only deltas (small)

This ensures crash recovery can reconstruct pages correctly.

Config: full_page_writes = on (default, recommended)

WAL Compression

-- PostgreSQL 14+ supports WAL compression wal_compression = on // Compresses full page writes using pglz or lz4 // Can reduce WAL size by 30-50% for write-heavy workloads // Trade-off: Small CPU overhead for compression Before compression: - Full page write: 8192 bytes - Compressed: ~3000 bytes (63% savings!) Impact: - Less disk I/O for WAL writes - Smaller WAL archive storage - Faster network transfer for replication

Replication Using WAL

Streaming Replication

Primary Server:

  • Generates WAL records
  • Sends to walsender process

Standby Server:

  • Receives WAL via walreceiver
  • Continuously replays WAL
  • Stays in sync (seconds behind)

Synchronous vs Asynchronous

Synchronous:

  • COMMIT waits for standby ACK
  • Zero data loss
  • Higher latency

Asynchronous:

  • COMMIT returns immediately
  • Possible data loss on crash
  • Better performance

🎯 Summary: Why WAL is Brilliant

The Big Picture

  1. Write-Ahead: Changes are logged BEFORE data is modified (durability)
  2. Incremental: Only changes are logged, not entire pages (efficiency)
  3. Sequential: WAL writes are sequential, very fast (performance)
  4. Continuous: No backup windows, no downtime (availability)
  5. Precise: Restore to any second in time (recovery flexibility)
  6. Replication: Same WAL mechanism powers standby servers (high availability)

🎯 The Golden Rule

WRITE TO WAL FIRST, THEN MODIFY DATA

This ensures that if the system crashes, PostgreSQL can replay the WAL to recover all committed transactions.

📊 Why WAL is Incremental

WAL only contains CHANGES (deltas), not entire data pages.

Example: If you update 1 row in a 1GB table, WAL only stores that specific change (~100 bytes), not the entire 1GB table!

🔄 Real Transaction Flow: How Changes Are Captured

UPDATE users SET balance = balance + 100 WHERE user_id = 12345; -- This simple query triggers the entire WAL mechanism below
1
Client sends SQL command

Query reaches PostgreSQL backend process

2
Parser & Planner work

PostgreSQL determines which rows to modify and creates an execution plan

3
🔥 WAL Record Created FIRST

Before touching the data page, a WAL record is generated containing:

  • Transaction ID (XID): 987654
  • Table OID: 16384
  • Block number: 42
  • Offset in block: 5
  • Old value: balance = 500
  • New value: balance = 600
4
WAL written to WAL Buffer

The WAL record is written to shared memory (WAL buffers) - very fast!

5
Data Page Modified in Shared Buffers

Now PostgreSQL modifies the actual data page in memory (not disk yet)

6
COMMIT - WAL flushed to disk

When you COMMIT, WAL is written to disk (fsync). Only then is the transaction durable!

📝 WAL Record Anatomy: What's Actually Stored

Example WAL Record Structure
LSN: 0/16B4408 // Log Sequence Number - unique position in WAL
XID: 987654 // Transaction ID
Resource Manager: Heap // Type of operation
Record Type: UPDATE
Block: 42 // Which 8KB block in the table
Offset: 5 // Position within block
Old Tuple: {user_id: 12345, balance: 500}
New Tuple: {user_id: 12345, balance: 600}
Size: ~120 bytes // Just this change!
LSN (Log Sequence Number)
0/16B4408

This is the unique position in the WAL stream. It constantly advances as changes occur.

🎯 Key Insight: The WAL record is tiny (~120 bytes) compared to the entire data page (8 KB). This is why WAL-based backups are incremental - they only contain changes, not full data!

📦 WAL File Management

WAL Segment Creation

PostgreSQL creates 16MB WAL segment files (default)

00000001000000000000000A

WAL Fills Up

As transactions occur, the current WAL segment fills with records

WAL Switch

When full, PostgreSQL switches to a new WAL segment

00000001000000000000000B

WAL Archiving

Old WAL files are archived (if archive_mode = on)

These archived WAL files are your INCREMENTAL backups!

-- PostgreSQL configuration for WAL archiving wal_level = replica -- Generate enough WAL for backups archive_mode = on -- Enable archiving archive_command = 'cp %p /mnt/backup/wal_archive/%f' -- %p = path to WAL file, %f = filename

💾 Real Backup Strategy with WAL

🏁 Base Backup (pg_basebackup)

📸 Takes snapshot of entire data directory
📍 Records starting LSN: 0/16B4000
💿 Size: 100 GB (full database)
🕐 Frequency: Weekly

📝 WAL Archiving (Incremental)

✏️ Only stores changes since last WAL
📈 Each WAL segment: 16 MB
💿 Daily WAL total: ~5-20 GB (varies by activity)
🕐 Frequency: Continuous (every 16MB or timeout)

Recovery Process

-- To restore to any point in time: 1. Restore base backup from Sunday 2. Apply WAL files in sequence: - Monday's WAL: 00000001000000000000000A-0000000F - Tuesday's WAL: 000000010000000000000010-000000015 - Wednesday's WAL: 000000010000000000000016-00000001B 3. PostgreSQL replays each WAL record: - Reads LSN - Applies change to data page - Advances to next LSN 4. Database reaches desired point in time!

🔬 Deep Technical Details

How PostgreSQL Writes WAL Records

Internal Process
1. Backend process calls XLogInsert()
   - Allocates space in WAL buffers
   - Copies record data to buffer
   - Returns LSN of inserted record

2. WAL buffers are 8MB circular buffer in shared memory
   - Multiple backends write concurrently (using locks)
   - WAL Writer process periodically flushes to disk
